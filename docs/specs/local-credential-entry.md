# Local credential entry for the Linux desktop pre-alpha

Superseded by the owner-accepted [shared secrets contract](shared-secret-storage.md).
The fixed physical-path dialog and Linux local-file default below are historical
proposals, not implementation instructions. Implement one managed-entry picker;
keep `system` as default and offer `local-file` only by explicit selection.

## Owner direction: generic secrets

The owner requested a general secret facility, usable by multiple extensions and
not tied to AI connections. A local file-backed store without a running keyring
is the initial target; an OS credential store can be offered later. Secret values
are not encrypted at rest by this choice and must not enter World exports. The
user can authorize individual components in individual scopes to read a chosen
secret. AI Provider is the first consumer, not a Core concept.

The native dialog and fixed AI connection binding proposed below are design
options, not settled implementation requirements. In particular, choose and
specify a generic secret-creation/selection flow and its caller authorization
before implementing browser entry. It must allow an existing secret to be shared
with separately approved consumers without giving them access to unrelated
secrets. Existing keyring entries must not silently disappear or be copied.

**Draft for owner approval.** Clicking **Manage API key…** on a saved AI connection opens a masked native Rintawa dialog. A user can paste a key, replace it, or delete it without opening a terminal or installing a credential service. The browser supplies the connection reference. The native Host owns both the input and its storage. The only new extension privilege is to request that dialog.

The frame CSP in `packages/web-runtime/src/http.rs` and the channel binding in `web/bridge/src/index.ts` isolate siblings, but a secret typed into a settings iframe is already available to its JavaScript. ## User flow and authority

1. Save the provider and its endpoint first. On a saved key-requiring connection, show **Manage API key…** in both baseline and World settings. The native dialog displays verified requester package/component, scope and exact secret path, plus the connection label and canonical endpoint explicitly identified as supplied by the extension. Use plain text for labels. Mark the key as shared by connections using this binding in this Rintawa home. Within the dialog show **No key saved** or **Key saved**, never characters from the old value. The empty password field supports paste and replacement. Save requires nonempty input. Delete is separate and requires confirmation. Cancel writes nothing.
2. Proposed browser-to-Host contract: one bounded `ui.manage-secret` request with exact path, sibling backend component ID and bounded display details. Dispatch through the existing authenticated channel as the mounted settings component. The Host derives the caller and resolves the sibling in that same active artifact, instance and scope. Manifest coverage of the exact path by the sibling and a new explicitly granted `secret-prompt` runtime permission on the calling component are both required. This grant can form part of the existing grouped installation consent for official settings in either scope. Neither possession of the path nor an existing read grant authorizes a dialog. No endpoint takes secret bytes. Use one Host-owned nonblocking native prompt, with at most one open across the desktop process; reject excess requests as busy. Keep the native submission tied to that request, owner and activation. Close on owner/channel loss, revoke or shutdown; order revocation against native commit admission. A completed commit survives a later disconnect. No automatic replay. Expose only completion/cancel/unavailable/stale outcomes to the caller. A lost reply means reopen the dialog to check its state.
3. A manifest can request a wide domain, and a permitted extension can suggest someone else's matching path. The prompt permission authorizes presenting a proposal only. Every write or deletion needs a separate native user action with the exact verified target visible. A caller cannot inspect even the presence of arbitrary keys by requesting this dialog. Native user consent remains the boundary against a misleading extension. Already authorized readers of this shared path can consume a replacement; deletion affects them all. A read grant and network access still require their own existing consent. A copied World gets its own approvals. A fresh home has its own values.
4. After dismissal, refresh the current saved connection and its ordinary health state. A user who saved a key but lacks provider access sees **Allow access…**. The next admitted provider read uses the latest committed value; rotation/deletion cannot recall bytes already returned or an in-flight request. Remove an old key before deleting a connection or changing its destination if desired. Confirm these operations with notice that the old key remains until explicitly deleted. Retain native exact-path CLI deletion for orphaned keys. Destination changes produce a fresh ID and a blank binding. A concurrent catalog change can orphan a key saved to the original path, but must never retarget it to a replacement ID. Refresh on conflict.

Implement the native input in the local desktop host. A missing graphical session reports that desktop entry is unavailable and offers the existing stdin CLI for that home. Keep the prompt outside the WASM execution lock and suppress values in widget diagnostics, command arguments, URLs, events, tracing and clipboard writes. Clear the input on dismissal. Do not promise erasure of browser/OS clipboard history. A browser form in the extension would be smaller, but would entrust the token to the whole browser delivery path. A separate loopback credentials website would add an authenticated second origin and session lifecycle just for entry. No new credential listener is needed for the native dialog.

## Local storage and compatibility

For the Linux application select the vault by resolved Host home in both the CLI and `HostRuntime::start` production engine construction. Add a file-backed implementation at the existing private `SecretVault` boundary. Preserve independently supplied managers and the existing system backend for embedders/future explicit selection. Cross-process readers see committed filesystem state. Keep grants separate in composition. Suggested layout is `<home>/credentials/<sha256-of-canonical-path>`, one raw bounded UTF-8 value per file. Hashing gives a fixed safe filename across currently valid CLI paths. No shared index or read-modify-write of unrelated secrets.

Require an owner-controlled private credential directory (0700), owner-owned regular files (0600) from creation, and safe parent path ownership/write permissions so another user cannot replace the directory. Reject symlink substitution and insecure existing entries; operate relative to a verified directory descriptor. Create replacements exclusively with mode 0600, write fully, sync, atomically rename in the same directory and sync the directory. Delete via unlink and directory sync. Concurrent writes to one key resolve in filesystem commit order. A reader sees a complete old or new value. Clean temporary files on ordinary failures and safely reclaim abandoned temporaries under exclusive writer coordination before subsequent modifications. Preserve the previous value on pre-rename failure. Report a post-rename/unlink sync failure as durability uncertain and ask the user to recheck. Distinguish missing from unsafe/corrupt/unavailable. Exclude the directory from application exports, templates, support bundles and logging. Full-home backups/copies include keys and need equivalent protection.

This default changes two accepted guarantees: Rintawa now stores plaintext protected by OS file permissions, and `--home` selects an independent vault. The OS account, root, processes with equivalent access, unprotected full-disk backups and an explicitly authorized backend can read tokens. File deletion does not guarantee physical erasure. Do not encrypt with an adjacent unattended key. No implicit fallback, copying or deletion of existing keyring entries. Existing installations using system credentials must re-enter their keys in each home that adopts this default; display this consequence in release notes. A future user-selected keyring can use the existing vault interface and will need an explicit switching/migration decision. The proposed Linux scope leaves other native platforms on their existing backend.

## Acceptance before shipping

- In a clean Linux desktop home without a keyring service, save a synthetic connection, paste a sentinel token, approve the exact provider access and verify a synthetic local server receives it. Restart Host, verify success again, replace it, then delete it. Check cancel and empty input. Verify the key is absent from captured bridge/WIT configuration payloads, logs, catalog, World SQLite and exported RTW. Include both baseline entry and World entry. Run a real GUI smoke, plus deterministic tests with an injected prompt driver.
- A different World using the shared connection and a fresh clone both need exact grants. Another component, detached frame, stale activation, wildcard path or caller lacking prompt approval cannot act on behalf of the settings component. Verify denied reads before approval, read revocation during I/O, no mutation on request alone, one concurrent dialog, and no stale submit after shutdown. A malicious caller cannot acquire key bytes or distinguish presence from indexed browser responses.
- Test stdin/GUI/runtime agreement and isolation for two homes; preserve CLI byte and length semantics. Exercise atomic concurrent replace/read/delete, pre-commit failure, crash cleanup, unsafe permissions/ownership, symlinked entries, corrupt/oversize input, lost reply and post-commit sync failure using only scratch homes. Confirm actual directory/file modes even under a permissive umask. Changing a destination never sends the old key to the new endpoint. Missing value, blocked read, unavailable storage and provider rejection have separate UI recovery.
- Approval authorizes the Linux file default, native prompt privilege and the narrow amendment to the previous native-entry policy. Implementation spans Core, the desktop Host, the browser bridge, official AI settings manifests and packaging of the chosen GUI dependency. No new World schema, secret-write WIT method or automatic privilege for previously installed extensions is required.
